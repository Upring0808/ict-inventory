# Security rollout and verification

## Deployment order

1. Take a recoverable Supabase database backup and run `lib/supabase/schema.sql` in a staging project. The script keeps existing equipment rows; it adds rate-limit storage, QR check-in enforcement, a service-only pending email approval table, and an `auth.users` trigger that follows confirmed email/password changes and invalidates older sessions. Email confirmation requires an approval made after current-password proof in the app. Apply the same script to production before deploying this version of the app. The copy at `public/supabase-schema.sql` is identical.
2. In Vercel, keep `SUPABASE_SECRET_KEY` (or its supported service-role alias) server-only. Set `INVENTORY_APP_ORIGIN` to the exact HTTPS origin for each environment that offers password recovery. Set `INVENTORY_RATE_LIMIT_SECRET` to a separate random value of at least 32 characters. If omitted, the server-only Supabase secret is used for keyed rate-limit identifiers. Do not prefix either value with `NEXT_PUBLIC_`. Add the deployed recovery URL to Supabase Auth's redirect allowlist. Protect previews or use a separate staging Supabase project.
3. In Supabase Auth, disable public sign-up, enable Secure password change, Require current password, and Secure email change. Enable password-changed and email-changed security notification emails. Configure SMTP, the reauthentication and recovery templates, Auth rate limits, and any CAPTCHA/WAF controls appropriate for public Auth traffic. These settings protect direct calls made to Supabase with the publishable key.
4. After the first authorized account exists, remove `INVENTORY_BOOTSTRAP_SECRET` from Vercel. The database bootstrap operation also refuses to create a second first account. Keep service-role access limited to server routes and rotate the service secret if it was ever exposed.
5. Deploy the app, then test an existing QR label while signed out and while signed in. Signed-out responses must contain only `propertyNumber`, `registered`, `equipmentType`, `brand`, `model`, `statusCategory`, and optional `yearAcquired`; signed-in staff should see the full record and be able to save a check-in. Test a wrong password, the rate limit and `Retry-After` response, a current-password account edit, email confirmation at both inboxes, a recovery link, both security notifications, and sign-out from another device. Test with an unauthorized Supabase Auth user as well as an authorized one; RLS must return no equipment to the unauthorized user.

The app's limiter uses a PostgreSQL upsert, so counters are shared across Vercel instances. It allows 8 login attempts per identifier and 30 per IP in 15 minutes; 5 setup attempts per IP per hour; 3 password-reset requests per email per hour; and 60 public QR lookups per IP per minute. It stores HMAC identifiers, not raw IP addresses or login names. Missing limiter configuration or schema causes protected routes to fail closed with HTTP 503. Vercel overwrites `X-Forwarded-For`; other hosting environments are treated as one unknown address until a trusted proxy is configured.

## Repository exposure

The local Git history shows `data/initialInventory.ts` containing real inventory data in initial commit `4590cfa` (2026-09-21). That file remained in later commits; replacing it in the current working tree does not erase earlier commit contents. No `.env.local` file is tracked in the current index. GitHub repository visibility and external clones were not verifiable from this workspace.

Treat the earlier file and any deployed JavaScript bundles containing it as exposed. Restrict repository access immediately if necessary, assess who could access the history and old Vercel deployments, and follow the organization's incident process for government inventory data. Coordinate a history rewrite with collaborators: keep a secure backup, use `git-filter-repo` or an equivalent tool in a clean mirror to remove the old data from **all** branches and tags, review the rewritten refs, then force-push during a planned window. Every collaborator must discard or reclone old history. Ask GitHub Support about cached views and pull-request refs; forks and existing clones require separate handling. Retire old deployments and cached build artifacts that included the starter data. A history rewrite does not change or delete Supabase production inventory rows.

The application now contains only fictional examples in the sample file, never seeds them into Supabase, and clears the local equipment cache on sign-out. Previously installed clients may retain cached data until they load this version and sign out; handle shared-device/browser storage according to organizational policy.

## Remaining operational checks

- The SQL migration and Auth settings must be applied and verified in the actual Supabase project; source review and local build cannot prove production policy state.
- The public QR label embeds the property number. If even that identifier is confidential, migrate future labels to opaque random references and retire old labels. Public registration checks are throttled, but a determined distributed caller can still probe identifiers over time.
- Supabase Auth endpoints are directly reachable with the publishable key. App-level login throttling supplements Supabase's own limits and edge protections; it cannot replace them.
- Password/email notifications depend on Supabase security-notification settings and working SMTP. Test delivery to both account holders after configuration.
- Supabase's security notification delivery still depends on project settings and SMTP. The source change cannot prove that messages reach recipients; verify delivery in staging before production rollout.
